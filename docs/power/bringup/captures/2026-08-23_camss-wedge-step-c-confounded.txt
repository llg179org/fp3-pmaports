1. THE DEVICE DID RESET, AND MY FIRST READING SAID IT DID NOT.
   uptime before the run: 951 s. uptime after: 1242 s. Rising - so I called it
   monotonic and concluded "no reset". Wrong: the run itself lasted about
   2000 s (53 + 126 + 503 + 74 + 626 + 611), so a device that had not reset
   would have read ~2950 s.
   ☠️ RULE: uptime-after > uptime-before is NOT evidence of no reset. It has to
   be compared against the ELAPSED WALL TIME of the run. Record the run's start
   and end on the host and check uptime_after >= uptime_before + elapsed.

2. THE MEASUREMENT IS CONFOUNDED, BY MY OWN EARLIER MISTAKE.
   The first fault of that boot is at monotonic 541 s:
       [ 541.772110] qcom-iommu-ctx 1e35000.iommu-ctx: timeout waiting for TLB SYNC
   but step C only started at 951 s. So the camera was ALREADY wedged when step
   C began. The wedge started during the previous attempt at the same run, which
   I had killed by leaving it in the foreground past a 10-minute cap.
   What this boot therefore does and does not support:
     - SUPPORTED: a camera-block-only run (`--only camera,suspend`) can start
       the wedge by itself - the killed attempt did, ~4 minutes in, with nothing
       but camera checks having run.
     - SUPPORTED: the wedge survives across a following run and ends in a reset
       19 minutes later.
     - NOT SUPPORTED: anything about step C's own contribution. It ran on an
       already-broken device.
   ☠️ RULE: before trusting a run, check that the kernel log's first fault is
   LATER than the run's start. A killed run can leave the device wedged and
   poison the next measurement.

3. THE TWO FAILURE MODES ARE LINKED AFTER ALL, AND CCI IS NOT REQUIRED.
   This one boot contains BOTH signatures:
       125x qcom-iommu-ctx ...: timeout waiting for TLB SYNC
         9x qcom-camss 1b00020.camss: VFE halt timeout
          1x rcu: INFO: rcu_preempt detected stalls on CPUs/tasks:

             (detected by 2, t=5252 jiffies, g=135369, q=1817 ncpus=8)
       [ 1691.461172] watchdog0: pretimeout event
   Earlier I wrote that the IOMMU wedge and the RCU stall were different failure
   modes "not to be called one bug until something links them". This links them:
   they co-occur in one boot, with the stall arriving 1131 s after the storm
   starts. A CPU spinning in a 5-second IOMMU timeout loop stalling RCU is a
   plausible mechanism, but that is a hypothesis, not a measurement.
   And: this boot contains ZERO `i2c-qcom-cci ... timeout` and zero `-110`.
   So the CCI timeout seen in step B is NOT necessary to reach the wedge.
   The common core across every reset so far is VFE halt + TLB SYNC storm.
