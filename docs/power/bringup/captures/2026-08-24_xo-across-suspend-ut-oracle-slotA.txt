UT-oracle across-suspend — does the downstream (UT 4.9 vendor) APSS master
enter XO shutdown across a GENUINE mem-suspend?  (slot a, 4.9.218-perf-ubuntutouch)

WHY: on pmOS (mainline 7.1.3) the APSS "xo_count" stays a hard 0 across
CONFIRMED rtcwake -m mem suspends (suspend_success increments), so the RPM never
aggregates to vlow. Question: is that a mainline regression, or an SoC/s2idle
limit that the downstream stack hits too? Same rpm_master_stats driver on both
sides -> apples-to-apples.

INSTRUMENT: /sys/kernel/debug/rpm_master_stats (downstream QCOM_RPM_MASTER_STATS),
per-master APSS "xo_count".  Forced suspend via echo mem > /sys/power/state with
the wakeup_count handshake, in a retry loop.

THE OBSTACLE (measured, in order):
 1. echo mem returns instantly (delta=0) — downstream honours wakeup sources even
    on a direct /sys/power/state write; pm_wakeup_pending aborts it.
 2. 7000000.ssusb is an active wakeup source that does NOT clear on cable unplug
    (dwc3 holds it — the same "USB controller stays active regardless of cable"
    seen on pmOS). Physical unplug alone did NOT let it suspend (ssusb still
    active after 240 s, all attempts delta=0).
 3. With ssusb wakeup disabled + the wakeup_count handshake, echo mem still
    aborted every time (writest=1 = -EBUSY): a steady ~5 wakeups/s from the
    MODEM IPC router (ipc_rtr_smd_ipcrtr / NasModemEndPoint / radio-interface)
    kept re-aborting the suspend sequence.
 4. rfkill lists only BT + WLAN — the cellular modem is ofono-managed (/ril_0,
    /ril_1), not rfkill-able.

THE FIX THAT WORKED: power both ofono modems off, disable ssusb wakeup, then run
the handshake-suspend loop. The first two windows (before other traffic resumed)
gave echo-mem exit 0 = genuine completed suspend/resume.

=== v4 (modem-off) DECISIVE RUN ===
-- BEFORE uptime=2320 --
APSS xo_count 0x0        <==== zero before
APSS numshutdowns 0x1e2e9
APSS active_cores 0x1
MPSS xo_count 0x1d3d   PRONTO xo_count 0x4886   LPASS xo_count 0x7d81
powering modems off...
attempt 0:  b=2324 a=2324 delta=0  cnt=16678 writest=1   (abort)
attempt 1:  b=2326 a=2333 delta=7  cnt=16782 writest=0   <== SUSPEND OK (exit 0)
attempt 2:  b=2335 a=2347 delta=12 cnt=16927 writest=0   <== SUSPEND OK (exit 0)
attempt 3..19: writest=1 (aborted once traffic resumed)
powering modems back on...
-- AFTER uptime=2425 --
APSS xo_count 0x2        <==== TWO XO shutdowns — exactly the two writest=0 suspends
APSS numshutdowns 0x1ec99
APSS active_cores 0x1
suspend_ok(loop flag) counts only delta>=15; the two 7-12 s real suspends are the
signal. xo_count 0x0 -> 0x2 is airtight: echo mem exit 0 == completed suspend, and
the counter moved by exactly the number of completed suspends.

=== CONCLUSION ===
The DOWNSTREAM APSS master DOES enter XO shutdown across a real mem-suspend
(xo_count 0 -> 2). pmOS/mainline never does across a confirmed s2idle suspend
(xo_count stays 0). Therefore the pmOS vlow=0 is a MAINLINE REGRESSION in the
msm8953 suspend path (the AP never votes its XO down in s2idle), NOT an SoC or
s2idle-inherent limit. The frontier is the mainline suspend/RPM path for APSS,
alongside the already-known LDO sleep-vote gap.

CAVEAT / not yet done:
 - Downstream reached XO shutdown only with the modem powered off; a tethered,
   radio-active downstream would not suspend either. The comparison is
   "completed suspend vs completed suspend", which is the right one, but the
   mainline side has NOT been retried with the modem off — pmOS suspended via
   rtcwake with the radio up (s2idle froze it). A cleaner mainline re-run with
   the modem quiesced would remove the last asymmetry.
 - active_cores reads 0x1 in every snapshot because the snapshot is taken after
   resume (core0 necessarily up); it is not evidence about the suspended state.
