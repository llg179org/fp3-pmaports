| [`modem-wakes-prior-art.md`](modem-wakes-prior-art.md) | ✅ **background, and one candidate excluded.** The closest prior art — a clock the AP holds blocking the modem's power-collapse handshake (SDM845 `axis2`, upstream `7cbb540a3a68`) — is **dead here**: mainline's msm8953 clock lists are identical to the vendor DT's, one grep. What survives: ModemManager registers NAS serving-system and signal-info indications unconditionally, and the kernel treats any IRQ arriving while device IRQs are suspended as a wakeup **by design** — so the fix is to stop generating the interrupt, not to handle it differently |
| [`rpm-idle-traffic.md`](rpm-idle-traffic.md) | ⏳ **new, and it replaces a retracted claim.** The ~35 Hz ring quoted for two days as the modem's is the **RPM's** edge; the modem's fires 0.07 times a second. The traffic is the AP's own: 15.5 `qcom_rpm_smd_write` a second, every one of them an interconnect bandwidth vote from a runtime-PM resume of the eMMC host. Raising `autosuspend_delay_ms` is the obvious knob and is **not yet demonstrated** - the A-B-A′ effect was the same size as its own drift, and the confound is that every leg ran over SSH |
| [`diag-bringup.md`](diag-bringup.md) | ⏳ **the instrument the modem lead now needs.** The DIAG channels are open on mainline from r78 (`CONFIG_RPMSG_CTRL` plus `RPMSG_CREATE_EPT_IOCTL`) and the modem's control channel talks — 2225 bytes, 30 packets, parsed. The data channel does not answer yet; the AP half of the handshake has to be copied from the vendor driver rather than guessed |
| [`vendor-kernel-sources.md`](vendor-kernel-sources.md) | 📚 which downstream kernel tree is which, and which one the oracle actually runs (**4.9.218**, UBports `halium-10.0`, fetched as `ut-halium-10.0`). ☠️ The branch name is the worst identifier — the branch *called* `ubuntutouch` is the old 4.9.112. Also: what the tree is for, and why diffing the whole thing is useless |
| [`modem-carrier-config.md`](modem-carrier-config.md) | ☠️ **CLOSED — the tenth dead candidate.** Both systems run the same modem configuration (`ROW_Commercial` active, platform package inactive), unchanged by a vendor boot, and PDC state is persistent so months of daily Ubuntu Touch use had every chance to set something else. ★ What it did find and is kept for: the oracle serves a 69-file AP-side MBN tree that pmOS does not have at all — a real difference in what the AP *could* hand the modem, just not one the modem acted on. Was: Elimination is exhausted and the network is no longer a variable — the oracle's windows were on the *expensive* cell too, at 5.4-8.1 % against our 48.9-52.7 % on that same cell. What is left has to be something the modem is told once and we never tell it, and there is one such layer the host owns: the carrier configuration (PDC/MBN). ☠️ Not `modem.mbn`, the firmware image, which is identical on both |
| [`modem-idle-lte.md`](modem-idle-lte.md) | ★★★★★ **the current lead, and it is the whole remaining idle gap.** The modem core is awake **34.8 %** on pmOS and **6.1 %** on the oracle — same hardware, same firmware, same operator and cell, both on LTE, measured with one instrument within half an hour. Every other candidate is dead. ☠️ And the cheaper system is the one doing *more*: it holds a live PDP context, we hold no bearer at all |
| [`lpass-never-sleeps.md`](lpass-never-sleeps.md) | ☠️ **two corrections since this page was written.** (1) "A master that never shuts down is a sufficient explanation for `vlow` reading 0" is **disproven** — LPASS was made to collapse for the whole of every suspend and `vlow` did not move; and the `vlow` hunt itself closed on 2026-08-24 when the oracle turned out never to reach it either. (2) The audio-clock fix shipped in r78 and **LPASS still records `XO total duration: 0` over a 600 s window**, against the oracle's 582.1 s. Priced at ~4 mA, so a correctness item today — but 7 % of what remains once the modem term goes |
| [`rpm-sleep-set.md`](rpm-sleep-set.md) | mainline's `qcom_smd-regulator.c` has exactly one `qcom_rpm_smd_write()`, hard-coded to the active state, where the vendor keeps `handle_active`/`handle_sleep` and a mandatory `qcom,set` bitmask. Fourteen LDOs vote active and never sleep. Both obvious patches are wrong, and the page says why |
